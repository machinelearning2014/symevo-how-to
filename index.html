symevo v2.0.0 · field reference

Evidence before conclusion

SYMEVO classifies a request as MATHS, CODE, or REASON, gives the model authority-specific tools, and refuses to finalize until the corresponding workflow checks pass. It exists to make the distance between “the model said so” and “this was checked” visible — and to make it a refusal, not a footnote.

The mental model

The name is a description, and the honest way to read this page is to take it apart. Symbolic because REASON requires an executable Prolog derivation, not prose. Evidence-gated because each authority has deterministic completion checks that run before a candidate answer can be published. Orchestrator because the model never picks the route.

The load-bearing sentence is this one: a temperature-zero model extracts what evidence a request requires, runtime-owned SWI-Prolog derives the shortest valid authority sequence from those facts, each authority executes its own native workflow, and a final-candidate verifier refuses to publish until the gates pass.

What makes it more than a prompt wrapper is where authority sits. The model classifies and reasons; it does not certify. Tool output cannot declare its own workflow completion, and the runtime-owned Prolog harness cannot be redefined by model code. Every terminal answer carries a status the model did not get to award itself.

The one sentence to remember

There is no separate model-generated task graph and no graph-level finalizer. The model extracts routing facts, trusted Prolog chooses the route, and each authority workflow remains authoritative for its own completion.

Where SYMEVO fits

This is a verification orchestrator, not a smarter chatbot. The three authorities are the clearest statement of what it is for, and they come with a filter.

The filter

  • The answer has a checkable form. A computation you can run, a change you can diff and test, or an argument you can derive from explicit premises. If “correct” has no mechanical witness, there is nothing here for a gate to consume.
  • You would rather be told INCOMPLETE than be told something fluent. The system is built to refuse. If a confident paragraph is what you actually need, this is a great deal of machinery for a worse experience.
  • You can state the premises. For REASON, the derivation is only as good as what you hand it — and SYMEVO verifies internal consistency, not premise truth. You remain the source of the premises.

What the three authorities replace

AuthorityEvidence that closes itWhat it replaces
MATHSa computation, a derivation with a frozen certificate, a constructed proof, or exact Lean source hashesa model asserting a result it may have hallucinated
CODEsource inspection, the post-mutation diff, and native build/test outputa patch that looks right and was never run
REASONan executable Prolog derivation with proof traces, consistency checks, and assumption-dependence testinga plausible argument with no stated premises

The wrong tool

  • Open-ended writing. There is no gate for prose quality, and no authority owns it.
  • Facts you need to be true. SYMEVO can ground a claim in a source you opened, but it does not verify that the source is right. Search results are discovery only.
  • Latency-critical paths. A turn runs a classifier, a Prolog process, an authority workflow, and a verifier. There is a per-turn deadline (default 30 minutes) and it is not a small number.
  • Anything where you want the model's own judgement trusted. That is the thing the architecture is built to not do.
Read this before trusting the gates

SYMEVO improves the traceability and internal validity of an answer. It does not turn a model into an oracle: source truth, source quality, and the correctness of translating natural language into a formal model all remain inside the trust boundary. Section 15 is the honest accounting.

The workspace guard

Launching evo-ai with a working directory inside the SYMEVO installation is refused, because an accidental writable workspace inside the tool’s own tree is how you corrupt the thing doing the checking. Pass --workspace explicitly if that is genuinely what you want.

Running the CLI

The CLI is flags-only. There are no subcommands — no serve, chat, or install verb. npm run serve is an npm script that runs a different entry point, and browser chat is a --chat flag.

evo-ai --workspace /path/to/repo "add a retry to the upload client"
evo-ai --chat                    # serve the browser chat and open it
evo-ai --chat-port 8080          # implicitly enables --chat

The evidence gates

Every authority has a native notion of evidence, and the gate is the set of obligations that must be satisfied before a candidate answer is published. The gates are deterministic checks, not another model opinion.

What counts, per authority

AuthorityRigorEvidence that closes the gate
MATHScomputationalpython_exec or sympy_exec with a computation check
derivationalmaths_problem stage=derive then verify_final
proofconstruction or exclusion evidence, then verify_final
formalproof rigor first, then Lean 4 verification against exact source hashes
CODE—source files, repository metadata, build and test output; source inspection plus the post-mutation diff plus native build/test
REASON—an executable Prolog derivation with proof traces, consistency checks, and assumption-dependence testing

The REASON rule is stated flatly in the system prompt: the Prolog derivation is the evidence. Not a description of one, not a summary of one.

What never counts

  • Model prose. Never evidence by itself. Model knowledge is not a tool result and must not be described as verified or externally sourced.
  • The inbuilt knowledge base. evo-kb.pl describes the runtime’s own tool and configuration surface. Its own header says it is “self-knowledge only … a premise source, not evidence; no verification gate consumes it.” The query_kb tool repeats the warning in its description.
  • Search output. Discovery only. Snippets must be registered as claims with ground_claims before anything may reason over them, and absence from a search is not proof of non-existence.
  • A matrix of green tool calls. Command success does not establish semantic relevance, and it is not proof that a test suite is exhaustive.
  • A consistent knowledge base. Consistency shows the submitted model derives its conclusion consistently. It does not show the premises are true.

How a candidate is gated

Two tiers. First, the workflow controller reports the first unmet obligation for the active authority — a missing problem_spec/1 artifact, a declared requirement that was never validated, an SMT obligation with no definitive verdict, a Lean obligation with no machine-checked proof, a diff that was never inspected. A candidate must also reproduce runtime strings verbatim: the REASON answer gate requires the seven canonical headings and exact copies of the runtime’s conclusions, assumptions, [DEPENDS] pairs, and requirement verdicts.

Second, the final candidate is evaluated once more — conflicting status declarations, dissolution approval, correctness certificates, and a regex that rejects forbidden Lean tokens: sorry, admit, axiom, unsafe, native_decide, exact?.

A rejection is not fatal. Feedback returns to the same loop. But rejections are bounded — after EVO_MAX_VERIFICATION_REJECTIONS (default 4) the turn returns INCOMPLETE.

The four terminal statuses

StatusMeans
SOLVEDthe requested conclusion was derived and every required check passed
MAPPEDthe task was a faithful mapping rather than a unique resolution — also the honest answer when a derivation yields no conclusions
INCOMPLETErequired evidence or verification is missing; this is the designed failure mode, not an error
DISSOLVEDa premise or framing defect invalidates the original problem — and this one costs extra (see section 09)

Semantic triage

Triage is called the Evidence Router, and its design rule is the most interesting thing in the system: the model extracts meaning, the runtime chooses the route.

A temperature-zero model run returns strict JSON and nothing else. It is a fact extractor, not a router. It reports the action, the target, the criteria the request implies, any operations requested, an explicit tier if you named one, and the proof mode. Then it stops. Model-supplied phases and evidence_requirements are ignored outright.

// what the model may say (schema_version 2)
{
  "action":  "prove",      // prove | review | diagnose | explain | how_to |
                          // implement | refactor | test | git | general
  "target":  { "id": ..., "description": ..., "source": ..., "support": ... },
  "criteria": ["mathematical_proof"],   // from a fixed vocabulary of 14
  "operations": [],                    // user-only attribution; never the model's request
  "proof_mode": "first_principles",
  "unresolved": [], "alternatives": []
}

// what the model may NOT say
//   "phases": [...]        -- ignored. the route is not the model's to pick.
//   "tier": "MATHS"        -- only honored when the user named it explicitly.

Targets are open-ended entity descriptions, not members of a fixed taxonomy — that was a deliberate change, so the extractor is not forced to bend a novel request into a known category. Provenance is checked: for facts attributed to the user, the context, or an observation, the quoted support must literally occur in that input.

That check buys traceability, and the documentation is careful about what it does not buy: a matching quotation does not prove that the model interpreted it correctly.

What Prolog does with the facts

% criteria map to the evidence kinds that satisfy them
criterion_evidence(argument_quality,    conceptual_derivation).
criterion_evidence(source_inspection,   workspace_source).
criterion_evidence(runtime_results,     runtime_behavior).
criterion_evidence(mathematical_proof,  mathematical_proof).
criterion_evidence(constraint_entailment, smt_entailment).
criterion_evidence(conceptual_proof,    lean_proof).

% obligations, then owners, then a shortest valid sequence
required(E) :- criterion(C), criterion_evidence(C, E).
required(assumption_analysis) :- criterion(assumptions).
required_owner(E) :- required(E), evidence_owner(E, Owner).

% the default is REASON only when nothing else is required or named
allowed(reason) :- \+ required(_), \+ explicit(_).

% a CODE -> MATHS -> CODE bridge must be a subsequence, not a jumble
bridge :- bridge_requested, allowed(code), allowed(maths).

Selection is shortest-phase-count, and the program enumerates candidate plans before cutting, so a cut can never hide a competing shorter plan. The search is bounded to 7 phases. Ties break stably by Prolog term sorting and are recorded as non-unique rather than silently resolved.

Planning optimizes nothing else. Not latency, not token cost, not model confidence, not expected success.

Routing statuses

StatusWhen
resolveda valid plan exists, evidence obligations exist, and no unresolved, unsupported, or alternative flags remain
needs_observationunresolved references, unsupported criteria, or no derived obligations at all
ambiguouscompeting interpretations were reported
inconsistentbridge requirements are unsupportable, or no valid sequence exists within the bound

A plan can be resolved and still carry unique: false. Uniqueness and resolution are independent.

The certificate

Every triage emits a certificate carrying the routing status, the extracted semantics, the plan, the evidence requirements and coverage, assumptions, the proof trace, and a SHA-256 of its own contents. Its engine is lite_reason_prolog, or degraded_deterministic if extraction or the Prolog call failed — in which case routing falls back to needs_observation and missing intent is not reconstructed from keywords.

What the certificate does not mean

Coverage means the plan contains an authority capable of owning an obligation. It does not mean evidence was collected or validated. The certificate is a planning record, not a proof of correct intent interpretation; its hash identifies the contents, it does not establish their truth.

When routing is unresolved, or when the model emits [REASSESS TRIAGE] on its own, the plan can be reassessed — at most three times per turn. Reassessment requires new successful observations after the first attempt, retains completed phases and the certificate hash, and freezes mutation and publish permissions. It cannot escape into an authority that was never planned.

Reasoning strategies

Behind a flag that defaults to off sits a portfolio of reasoning operators, each implemented as a Prolog search over an explicit finite model. It is the most experimental part of the system, and the code says so.

# the only two accepted values; anything else throws at startup
EVO_REASON_STRATEGY_MODE=on
EVO_REASON_STRATEGY_MODE=off    # default

With the portfolio off, the reason_strategy tool is not even registered, and the controller fails with Strategy portfolio is off (EVO_REASON_STRATEGY_MODE=off). The tool takes describe, status, and solve.

The operators

Operators are organized into five layers — reformulate, derive, explore, complexity, verify — and the available set includes deduction, forward chaining, working backwards, constraint satisfaction, counterexample search, optimization, generate-and-test, reduction, abstraction, analogy, recursive decomposition, divide-and-conquer, dynamic programming, search, means-ends analysis, greedy, randomized exploration, hypothesis-test-revise, and abduction.

Seven operators are registered but explicitly unavailable, and the distinction is enforced in the registry rather than left to documentation: induction, causal_reasoning, simulation, adversarial_reasoning, invariant_discovery, relaxation, approximation.

Selection is deterministic

Problem shapeDefault operator
logicworking_backwards
graphdynamic_programming
hypotheseshypothesis_test_revise
allrecursive_decomposition
has a claimcounterexample_search
has an objectiveoptimization
anything elseconstraint_satisfaction

strategy=auto uses that table; naming an operator directly requires it to be eligible. Repeating an unchanged attempt is blocked — “Repeated unchanged strategy attempt blocked; inspect its result or materially revise the problem.” Budgets are shared and reserved up front: 20,000 work units, 24 attempts, depth 20, 10 seconds.

Outcomes that refuse to overclaim

An attempt reports one of proved, refuted, feasible, optimal, plausible_hypothesis, infeasible, or unknown, and always carries the scope submitted_finite_model. Results are validated outside the solver — witnesses are rechecked against the original domains, proved requires exhaustive search, and a decomposition only counts as proved if every child was accepted. An unknown outcome becomes inconclusive with the reason kept intact: “No conclusion followed within the submitted finite model; uncertainty retained.”

The harness narrates its own limits in the code, which is unusual and worth quoting:

  • “Positive Horn closure; failure to derive does not prove negation.”
  • “No feasible assignment found. Inconsistent premises do not prove a claim.”
  • “Missing predictions are not confirmation. Suggested tests have not been performed.”
  • “a greedy dead end is not proof of impossibility”
Why this ships off

The design plan is explicit that promotion requires a predeclared, task-stratified improvement target at an agreed cost ceiling, and that publishing a taxonomy or adding prompt instructions does not satisfy it. Until then the portfolio stays behind EVO_REASON_STRATEGY_MODE=on. The tool’s own contract says results “never establish premise truth or model adequacy.”

Prolog and the knowledge base

SWI-Prolog is not a library call here — it is the symbolic layer, and the runtime owns the harness so the model cannot replace it.

Four .pl assets ship with the runtime, each stamped “do not edit or redefine”:

FileRole
reason-harness.plappended to every prolog_exec call; provides the proof, consistency, dependence-testing, and requirement-reporting predicates
claim-contract.plinjected after ground_claims to bind grounded premises to their sources
strategy-harness.plthe portfolio solver; its input is JSON data, never executable model-supplied Prolog
evo-kb.plthe generated self-knowledge base

For prolog_exec the model writes only a declarative knowledge base; the harness supplies everything else, and each call is isolated. Resource limits are deliberate: a 256 MB Prolog stack, a 25-second Prolog execution limit, and a 30-second outer process timeout with cancellation support.

The REASON workflow runs R1 SETUP through R6 ANSWER, and the step whose failure is most instructive is R4, the assumption-dependence test: the harness retracts and reasserts each assumption to see which conclusions actually depend on it. The system prompt warns that an assumption declared as a static rule rather than a dynamic fact survives retraction and makes the test useless — a silent way to pass a check that did nothing.

The knowledge base is not evidence

This is the distinction most likely to be misread, so the codebase states it in three places. evo-kb.pl is self-knowledge: it describes the runtime’s own tools and configuration. Its header says it is “a premise source, not evidence; no verification gate consumes it.” The query_kb tool description repeats that the self-knowledge “is not verification evidence.” And the knowledge base’s own status predicate reports its size — at generation time, 74 tools and 75 configuration keys.

Two other query surfaces exist and are easy to confuse with it. query_kb exposes session predicates such as recent_messages/2, messages_about/2, tools_used_list/1, and search_conversation/2. query_proof_kb exposes the proof ledger: verified_lemmas/1, proof_errors/1, goal_snapshots/1, tactics_for_goal/2, errors_for_goal/2, similar_to/2.

The honest caveat on the symbolic layer

Prolog is deterministic given the extracted facts. Its largest remaining vulnerability is a plausible but incorrect semantic extraction: if the model supplies a wrong interpretation or omits an important criterion, Prolog will produce a valid plan for the wrong question. Determinism downstream does not repair a misunderstanding upstream.

Independent review and dissolution

DISSOLVED is the one status a model cannot award itself. Claiming a request is unanswerable is the most consequential thing an agent can say, so it costs an extra review with its own evidence requirements.

The rule: a status label, a consistent Prolog knowledge base, or a model-authored list of fulfilled requirements cannot establish that the user’s request is unanswerable. When a candidate declares DISSOLVED, the runtime makes a separate temperature-zero model call with no tools, handing it the original request, the candidate, the reference context, and the current phase’s tool records.

Approval is not a vibe. Every one of these is validated in code before the status is accepted:

  • approved === true, and request_preserved — the reviewer is judging the request that was actually asked
  • whole_request_blocked and blocking_demonstrated — the whole request, not a convenient part of it
  • reasonable_repair_available === false — no reasonable interpretation salvages it
  • an empty unsupported_assumptions list
  • a nonempty premise_quote that literally occurs in the original request
  • at least one interpretation, every one of them marked answerable === false
  • exact quotes of tool output — failed, truncated, or non-matching citations invalidate the approval

The approval is bound by SHA-256 to the request, the candidate, and the full current-phase tool snapshot. A later candidate cannot reuse an earlier approval. A bare DISSOLVED with no approval is rejected with a message that says exactly why:

[SYSTEM] DISSOLVED requires independent review of the original request,
blocking evidence, and reasonable interpretations. A status label or
successful derivation alone cannot authorize dissolution.

The reviewer sees the latest 12 tool records from the current phase, each truncated to 12,000 characters. The request and the candidate are never truncated. A truncated record cannot serve as an accepted citation, which closes the obvious trick of citing something the reviewer could not read.

This is a challenge, not a second opinion from a stranger

The review is a separate call to the configured model — not an independently trained verifier — so it can share the generating model’s biases. Quote matching validates provenance, not semantic entailment or source truth, and a mistaken review can still misclassify a genuine defect. What the gate adds is an explicit challenge that fails closed when review evidence is missing. It does not establish completeness of all possible interpretations, and it is not a general semantic audit of every answer.

The CODE workspace

CODE is the authority where evidence is easiest to fake and easiest to check, so the workflow is built around one question: what did you actually observe, and what did you actually run?

The workflow is K1 INSPECT through K5 ANSWER, and the gate consumes three things: that the sources were inspected, that the post-mutation diff was inspected, and that a native build or test actually ran. A directory listing, a web result, a scratch pad, a subagent’s answer, or a Prolog fact are all explicitly not exact-source evidence for CODE.

read / ls / grep / symbols     # inspect — the evidence base
edit                            # atomic, revision-checked; replace_text never truncates
undo                            # revert
bash                            # verification commands set codeVerified=true
verify_plan                     # plan checks must be verified
code_sandbox_run                # ephemeral OS sandbox, network off by default
publish                         # gated on the above

edit is revision-checked and atomic, and its replace_text mode is documented as the preferred way to edit precisely because it never truncates the file. Destructive bash commands are refused. Verification commands — test, check, build, lint — are the ones that set codeVerified.

Where CODE evidence stops

The CODE authority documentation is candid about the edges of its own guarantee, and two of them matter if you are going to rely on this:

  • No guarantee against concurrent writes after the last observation, and no proof that a test suite is exhaustive. The diff you inspected is the diff that existed when it was inspected.
  • A Lean proof about a model of your source is not a proof of your source. That evidence is tagged assurance: source_linked_model_proof with implementationBound: false, and an implementation-bound formal request cannot complete or publish on it. Closing that gap needs a trusted source-to-model refinement checker — not another model assertion.

Source-anchored review notes remain an optional review ledger, explicitly not a completeness certificate.

Formal and mathematical work

MATHS is the deepest authority, and the one where the system is most insistent that a proof about the wrong statement is worse than no proof at all.

The workflow runs M0 START, M1 MODEL, M2 EXPLORE, M3 DERIVE, M4 VERIFY, M5 ANSWER. Rigor determines what closes it, and formal rigor is two-phase: the proof phase runs M1–M4 to produce a frozen mathematical certificate, and only then does the Lean extension phase begin — prove_problem start, a statement skeleton, then either a direct track or a decomposition track, ending in verify_final.

The gate rejects the standard ways of faking a Lean proof. A regex refuses sorry, admit, axiom, unsafe, native_decide, and exact?. Evidence is bound to exact source hashes. A failed proof route is deferred and replanned — never silently treated as proved.

If the formal phase times out, the frozen mathematical certificate is still rendered as the answer, and only the Lean formalization is marked incomplete. That is a deliberate separation: the maths was done, the mechanization was not.

Formal recovery

When a Lean proof stalls, recovery is guided rather than blind. The controller renders its allowed next actions as workflow guidance, and a frontier_plan accepts Lean identifiers only — pending lemmas must be registered with an exact statement and dependencies before they can be probed or delegated, and registration rejects unknown dependencies and cycles.

Failed executions and probes increment the registered frontier’s attempt count; missing arguments and protocol errors do not. At EVO_AUTO_SPLIT_THRESHOLD (default 3) the controller suggests specialist workers, then explicit decomposition.

What formal recovery does not do

A generic type mismatch is not treated as evidence that an equality is reversed, and resolution statistics are not inferred merely because a later candidate succeeded. The checks establish integration behavior — not a measured improvement in model success rate or runtime. And a constructed-proof guard is a conservative source-level check, not a Lean proof-term provenance verifier: it does not establish resistance to arbitrary aliasing, tactic-generated wrappers, or semantic reformulation.

Parsing behavior worth knowing

  • Integers ignore zero and negatives. The parser requires a value greater than zero and otherwise falls back to the default — so EVO_MAX_TURN_MS=0 does not mean “unlimited”, it silently means 1,800,000.
  • Booleans are permissive. Anything not in disabled, off, false, 0, or no reads as true. Setting a variable to a value you did not intend can enable a feature rather than disable it.
  • EVO_REASON_STRATEGY_MODE is strict, and throws on anything that is not exactly on or off — the opposite of the boolean rule above.
Undocumented variables ship silently

EVO_RG_PATH, X_API_BEARER_TOKEN, and the legacy TWITTER_* aliases are read by the code but appear in no documentation. The reason is a gap in the coverage validator: it scans a fixed list of seven files and does not include workspace-tools.ts or x-tools.ts, so variables read there never fail npm run docs:check.

One documented default deserves a callout rather than a footnote: the Gmail integration ships a non-placeholder default account address in .env.example and in the generated configuration reference. Set GMAIL_ACCOUNT explicitly rather than relying on the default.

Gotchas

  • --no-stream does nothingThe flag is parsed into a field that is never read again. The --help text (“Disable streamed one-shot output”) is misleading; the README correctly calls it an accepted compatibility flag.
  • --extra-workspace is hiddenA real, repeatable flag that appears in neither --help nor the README. Only its environment equivalent, EVO_EXTRA_WORKSPACES, is documented.
  • --chat-port turns chat onPassing a port implicitly enables --chat and opens a browser to a token-bearing localhost URL.
  • The log path documented in the README is wrongThe README says logs default under .evo/logs/. The code defaults to <EVO_ARTIFACT_ROOT>/logs/evo.log. EVO_LOG_PATH overrides both.
  • No --version, no --There is no version flag and no argument terminator. Any unrecognized -x throws.
  • EVO_REQUIRE_LEAN is a startup gate, not a runtime oneIt makes the public server fail to boot when the Lean smoke proof cannot run. Without it, the server deliberately continues with the Lean tools disabled.
  • Missing JWT_SECRET is a hard boot failureThe server refuses to start, and the error message explains the alternative: every session token would be forgeable.
  • code_worker is a stubIt is registered as an unavailable compatibility adapter and tells you to use evo_subagent instead.
  • Documented tools may be unavailableThe docs generator hard-codes the strategy portfolio as enabled so it can document the full tool surface. At the default EVO_REASON_STRATEGY_MODE=off, reason_strategy is not registered at all.

What it does not claim

The most valuable documentation in this project is the part that argues against trusting it. Collected here, because a field reference that only lists capabilities is a sales page.

The gate verifies consistency, not truth

The REASON authority verifies that a conclusion follows from the premises it was given. It does not verify the truth or the provenance of those premises. Under conversational pressure the model can confabulate under induced coherence pressure — and because the verifier checks consistency with the chosen premises, a confabulation passes the gate as SOLVED.

A 28-turn stress test named five failure modes: circular premise, fact-laundering, user-premise assimilation, history confabulation, and prompted-only insight. The first mitigation was implemented and tested live, and the result is reported with unusual honesty: it forced a non-circular derivation, and “the confabulation did not disappear — it relocated”, moving the contested claim from an observation into an assumption and coining a fake epistemic kind. The conclusion recorded in the roadmap is that it is “a proven point-fix; it is insufficient alone.” The second mitigation shipped only as an advisory slice — it emits a reversal signal and does not reject the answer, pending a false-positive rate on real runs. Binding is deferred.

Triage is a planning record

The router’s determinism is downstream of a model extraction, and that extraction is the weak link. Substring provenance checks establish that a quote occurred, not that it was understood. The certificate hash identifies its contents; it does not establish their truth. A passing evaluation run is a small regression sample, not a guarantee of intent understanding.

Identity matching has a known hole

Three different normalization functions are used in different gates — normalizeExact, canonicalIdentity, and normalizeForComparison — with the result that the same drift can be tolerated by one gate and rejected by another. A fuzzy-matching second layer is designed but not implemented, and the documented decision is to keep it off the binding path until its false-accept rate has been measured.

The reviewer shares the model’s biases

Dissolution review is another call to the same configured model, not an independent verifier. It adds an explicit challenge and fails closed on missing evidence; it does not establish that all reasonable interpretations were considered.

The portfolio is unproven, and says so

The reasoning strategy portfolio defaults to off and remains gated on promotion criteria that have not been met. Seven operators are registered as unavailable. Results are scoped to a submitted finite model and never establish premise truth or model adequacy.

Formal work is integration-tested, not benchmarked

Formal recovery establishes that the mechanisms connect correctly — not that the model succeeds more often or runs faster. The constructed-proof guard is a conservative source-level check, and the project states plainly that it does not establish resistance to aliasing, tactic-generated wrappers, or semantic reformulation.

The sentence the project keeps repeating

SYMEVO improves the traceability and internal validity of an answer. It does not turn an LLM into an oracle. Source truth, source quality, and the correctness of translating natural language into a formal model remain part of the trust boundary — and no amount of Prolog moves them out of it.
